## Result and architecture

One explicit organization owner can create projects, save email/domain admission rules, remove organization people and assign explicit project access. Saved emails do not depend on account existence. Exact verified email/domain rules apply within the next verified login transaction without acceptance. Organization joining grants no project access and never links identities by email. Removal clears project grants and stores email/stable-user exclusions; a later verified email change cannot silently undo removal. Allowing joining removes exclusions only; it restores neither membership immediately nor old project grants.

- Canonical `people.py` contracts define validated normalized ASCII email/domain inputs, owner/people/rule pages and per-person project deltas. HTTP metadata regenerates ignored OpenAPI/SDK/Zod/TanStack artifacts. Natural-key rule saves support safe retry; missing/foreign delete targets consistently return404, and owner removal/conflicting backfill returns409.
- Migration `0004_owner_admission` follows `0003_access`: nullable explicit owner constrained to organization membership, admission provenance, email/domain rules, email/user exclusions and rule audit identifiers. Existing organizations receive no inferred owner. Operator bootstrap and one-time `assign-owner` choose a specific existing verified member; owner transfer/revocation is excluded.
- `people_store.py`, `people.py`, `people_http.py` implement bounded owner administration. Live session/CSRF/current owner are rechecked within the write transaction. Organization locks serialize login and administrative changes; audits commit with mutations. The organization discovery join explicitly uses membership.organization_id, avoiding ambiguity from the new owner foreign key.
- `enrollment.py` re-reads matching rules after organization locks inside the identity session-establishment transaction. Narrow optional verified-login injection and bounded display lookup extend actual identity services without importing identity ORM rows into access application code. No session-read admission, scheduler, replacement auth system or bypass route exists.
- Owner authorization applies to first project creation and replay, preserving P07 idempotency and explicit creator grants. `AccessStore.require_project(user_id, project_id)` and its ordinary two-membership resource policy remain unchanged for P08 consumers; owning an organization grants no implicit project-resource access.
- Actual `AuthenticatedApp` routes `/settings/orgs/{orgId}/people` through P06.5’s epoch-bound AuthBoundary. Settings links to it and uses the real owner summary to gate creation. The explicit demo remains separate.
- Validated SDK/query wrappers compose generated operations, validators and query keys. Focused query/mutation/access hooks preserve CSRF, final session-epoch validation, bounded pagination, cache invalidation, pending guards and protected-data cleanup. Project writes affect only edited people, preserving unseen page assignments. Previous pages remain visible during fetch, and project assignment controls disable during refresh.
- Approved MUI presentation uses canonical types and named callbacks. Local email/domain and project drafts are scoped to user/organization and survive tab/page navigation or temporary read errors. Protected content is hidden until access is rechecked. Confirmed access denial, identity retirement or organization changes discard drafts. Empty pagination/removal sections are omitted. Failure input, confirmation distinctions and success focus are preserved.
