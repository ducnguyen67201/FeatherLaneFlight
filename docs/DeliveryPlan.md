# FeatherLaneFlight delivery phases

Status: delivery roadmap; implementation proceeds through phase dispatch and UI approval gates. Updated October 28, 2026.

The [engineering specification](EngineeringSpec.md) describes seven broad stages. This plan breaks its first PX4/SIH deliverable into **24 small-to-medium phases**. Each phase produces a reviewable increment with a clear completion boundary. Customer-facing release checkpoints are identified separately from mock demonstrations and internal capabilities.

Already complete: architecture documentation, [design rules](../DESIGN.md), [design tokens](../design-tokens.json), the local UI UX Pro Max skill, and [coding/approval rules](../AGENTS.md). Phase execution is tracked in the registry; the rendered UI preview still requires approval.

Each phase now has a small [engineering implementation plan](phases/README.md). The master-owned [registry](phases/registry.json) records its chat, dependencies, approvals, PR, and merge state. Staged chats stay read-only until dispatched; UI previews require explicit human approval before implementation. Completed phases require a separate submission approval before their branch is pushed and PR opened; the user decides merging, which normally gates the next phase.

## Rules for a phase

- **Small:** one narrowly bounded capability or configuration/documentation deliverable. **Medium:** one coherent workflow across the necessary UI/API/runner boundaries. Size describes scope, not a promised duration.
- Add only the contracts, routes, fields, and fixtures needed for the current phase. Extend the canonical models and regenerate the client alongside later features. Avoid defining every future integration up front.
- Every UI task follows **rendered preview -> explicit user approval -> implementation -> manual verification**. A phase can pause at its approval gate. A roadmap approval does not approve an unseen UI. Existing approval remains valid for unchanged scope.
- Minimal isolated preview code/mock data is allowed before UI approval. Keep previews separate from application implementation and live integrations.
- Before completing a phase, manually demonstrate its main behavior and relevant failure case, run applicable existing checks, and record any limitation. Agents do not write application automated tests unless requested; the user owns that work.
- If a phase develops multiple independent workflows or a large review surface, split it before continuing. Do not enlarge a phase to preserve the count.
- A phase completion does not authorize pushing, publishing, deploying, or changing third-party infrastructure. Release preparation produces a concrete candidate for the user's deployment decision.

## Dependency and scope notes

The default order is sequential. P18's isolated build/host compatibility spike can begin after P01 while UI feedback is pending; a qualified report must exist before P19. Actual mission execution still depends on the completed supervisor, evidence, and finalization gates through P17.

Registering a build or publishing a suite does not qualify a real integration. P08-P17 use an explicitly identified fake integration and synthetic evidence where needed; its qualification record must exist before P12. Real capability visibility follows its own evidence gate: nominal after P19, ground GNSS verification after P20, and airborne response after P21. P18 alone does not enable real mission options. A candidate that changes simulator/sensor physics or other comparison-critical inputs requires renewed qualification rather than a default regression verdict.

Pre-publication qualification uses a local operator workflow with owned processes and recorded evidence. Publish the verification record before exposing that capability through normal run admission. This prevents a circular requirement to admit an unverified scenario in order to qualify it; normal API admission never gains a verification bypass.

Apply authorization, input validation, version checks, bounds, redaction, and audit writes in the phase that introduces the relevant capability. P23/P24 assemble operational behavior and evidence; they are not catch-all phases for missing correctness.

This roadmap covers the first simulation-only PX4/SIH workflow in the engineering spec. Additional flight stacks/simulators, GPU perception, customer autonomy-process execution, real aircraft/hardware testing, managed execution, marketplace/data licensing, invitations, and web membership/retention editing belong to later plans.

The declared manual, automated, and real-SITL release checks still determine release readiness. The user owns new automated tests unless they explicitly delegate them. A roadmap milestone, mock success, or one successful simulation does not establish real-world reliability or deployment approval.
